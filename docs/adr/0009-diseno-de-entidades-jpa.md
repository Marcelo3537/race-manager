# 0009 — Diseño de las entidades JPA

- **Estado:** Aceptada
- **Fecha:** septiembre de 2026
- **Relacionadas:** [0007](0007-flyway-y-validacion-de-hibernate.md), [0012](0012-dtos-con-records-y-mappers-manuales.md), [0013](0013-open-in-view-desactivado.md)

## Contexto

Las entidades tienen que satisfacer los requisitos de JPA (por ejemplo, un constructor sin argumentos) sin permitir que el propio código cree objetos incompletos o manipule valores que no le corresponden.

## Decisión

- **Clave primaria generada por la base de datos:** `BIGINT GENERATED BY DEFAULT AS IDENTITY` en SQL y `@GeneratedValue(strategy = GenerationType.IDENTITY)` en Java.
- **`Long` y no `long` para el id**, y `Integer` para los números opcionales o recién creados. Un id `null` significa "aún no guardado", y `save()` usa esa información para decidir entre `INSERT` y `UPDATE`.
- **Sin `setId()`.** Nadie salvo la base de datos asigna identificadores.
- **Constructor sin argumentos `protected`**, exigido por JPA y fuera del alcance del propio código; y **constructor público con los campos de negocio**, para que no se pueda crear una entidad a medias.
- **`@Column` refleja la tabla** (`nullable`, `length`, `precision`, `scale`) para que la validación de Hibernate detecte discrepancias.
- **Sin `equals` ni `hashCode` por ahora.** Se diseñarán al llegar las relaciones, porque el id nulo antes de guardar y los proxies perezosos hacen que las implementaciones ingenuas fallen.
- **Actualización por *dirty checking*:** el servicio modifica la entidad gestionada dentro de la transacción y no llama a `save()`; Hibernate compara con la copia que tomó al cargarla y emite el `UPDATE` al confirmar.

## Alternativas consideradas

- **`GENERATED ALWAYS AS IDENTITY`.** Impediría insertar ids explícitos en datos de carga o en migraciones de corrección.
- **Estrategia `SEQUENCE`.** Permite inserciones por lotes, a cambio de más configuración que hoy no aporta nada.
- **Lombok (`@Data`, `@Getter`...).** Reduce código, pero oculta lo que hace la clase y `@Data` genera `equals`/`hashCode` peligrosos para entidades.

## Consecuencias

**Positivas**

- Es imposible construir una entidad sin sus datos obligatorios desde el código de negocio.
- Los identificadores los controla exclusivamente la base de datos.

**Negativas o costes**

- Getters y setters escritos explícitamente (se generan con el IDE).
- `equals` y `hashCode` quedan pendientes para cuando haya colecciones de entidades.
